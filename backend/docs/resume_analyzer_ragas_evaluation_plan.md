# RAGAS Evaluation Pipeline for the `resume_analyzer` Agent

## Context

The `resume_analyzer` CrewAI agent (`backend/app/services/crew/agents.py:187`) extracts a resume's raw text into a strict `ParsedResume` JSON document. Today the only quality check is a CrewAI `HallucinationGuardrail` (a no-op on open-source CrewAI) and an ad-hoc isolation script (`backend/tests/run_resume_analyzer_test.py`). There is **no objective, repeatable measure** of extraction quality.

This plan adds a RAGAS-based evaluation pipeline that scores the agent's JSON output against a hand-verified golden dataset on three metrics: **faithfulness, answer_relevancy, answer_correctness**. The outcome is a versioned dataset the team maintains and a runner that produces per-sample and aggregate scores, so prompt/model changes to the agent can be measured rather than guessed.

### RAGAS field mapping (decided)

| RAGAS field | Source | Notes |
|---|---|---|
| `user_input` (question) | The `_resume_analysis_task` description (`backend/app/services/crew/tasks.py:92-151`) | Same for every sample; extraction instruction + embedded schema |
| `retrieved_contexts` (context) | **Raw extracted resume text**, passed whole as a single-element list | The agent's true input (from `extract_resume_text`), not the parsed JSON. Still required — `faithfulness` and `answer_relevancy` both consume it. No chunking. |
| `response` (answer) | The agent's parsed JSON (`ctx.state["json"]`), **verbalized** to statements | Generated live by running the agent |
| `reference` (ground truth) | Human-verified `ParsedResume` JSON, **verbalized** the same way | **The team provides this** |

### Per-metric requirements

| Metric | Fields used | Needs LLM | Needs embeddings |
|---|---|---|---|
| `faithfulness` | user_input, response, retrieved_contexts | ✅ | — |
| `answer_relevancy` (`ResponseRelevancy`) | user_input, response, retrieved_contexts | ✅ | ✅ |
| `answer_correctness` (`AnswerCorrectness`) | user_input, response, **reference** | ✅ | ✅ |

## What you need to provide

1. **Ground-truth JSON per sample resume (the main deliverable).** For each sample, a hand-verified `ground_truth.json` in the exact `ParsedResume` schema (`{"id": int, "result": {...}}`, models at `backend/app/services/resume_parser.py:254-296`). Seed each from the already-generated (but **unverified**) outputs in `backend/tests/output/` (e.g. `test_parsed_resume_Arijit_De_Resume_2026_*.json`), then correct by hand — fix wrong dates, missing positions, mis-categorized skills, hallucinated fields, etc. This is what "correctness" is measured against, so its accuracy matters most.
2. **Working API keys** in `backend/.env` (live-only mode): `ANTHROPIC_API_KEY` for the agent generation step (the resume_analyzer runs on Claude, `claude_llm_extraction`), and `GEMINI_API_KEY` for the RAGAS judge LLM + Google embeddings.
3. **Source resumes** — the 3 in `backend/sample_data/` are the starting set (`Arijit De Resume 2026.*`, `Yash_Pal_Resume.pdf`, `Yash_Raj_Singh_Oct_Resume.pdf`). Add more for a stronger dataset; each needs a matching ground truth.

You do **not** provide: the question (derived from the task), the context text (auto-extracted from the source resume), or the answer (generated by running the agent).

## Implementation

### 1. Dependencies
Add RAGAS to the dev group with uv (run from `backend/`):
```
uv add --group dev ragas
```
RAGAS pulls `datasets` and `langchain-core` transitively; `langchain-google-genai` is **already a dependency**, so Gemini wiring reuses it. Watch for resolver friction against the pinned `fastapi>=0.115,<0.116` — RAGAS doesn't depend on FastAPI, so a conflict is unlikely, but confirm `uv lock` succeeds.

### 2. Gemini wiring — `common/gemini.py`
Reuse the existing `langchain-google-genai` package. Bridge the env var (`langchain-google-genai` reads `GOOGLE_API_KEY`; the repo uses `GEMINI_API_KEY`) by passing the key explicitly:
```python
from langchain_google_genai import ChatGoogleGenerativeAI, GoogleGenerativeAIEmbeddings
from ragas.llms import LangchainLLMWrapper
from ragas.embeddings import LangchainEmbeddingsWrapper
from app.core.config import get_settings

def build_evaluator():
    key = get_settings().GEMINI_API_KEY
    llm = LangchainLLMWrapper(ChatGoogleGenerativeAI(
        model="gemini-2.5-flash", temperature=0, google_api_key=key))
    emb = LangchainEmbeddingsWrapper(GoogleGenerativeAIEmbeddings(
        model="models/gemini-embedding-001", google_api_key=key))
    return llm, emb
```
Note: the embedding model is `gemini-embedding-001` — `text-embedding-004` was retired by Google (404). A small compat shim (`tests/ragas/common/compat.py`) is required before `import ragas`: ragas 0.4.3 eagerly imports a `ChatVertexAI` module that langchain-community 0.4.x (langchain 1.x line) removed; the class is only used in an isinstance whitelist, so a sentinel stands in safely.

### 3. Verbalizer — `common/verbalize.py`
The parsed JSON has ~40 fields, many empty; feeding raw JSON produces noisy claims ("twitter_url is empty"). Convert only **populated** fields of a `ParsedResumeResult` into natural-language statements (e.g. "Worked as Senior ML Engineer at Acme from 2021-01-01 to present."). Apply the **same** verbalizer to both the agent answer (`response`) and the ground truth (`reference`) so `answer_correctness` compares like-for-like. Function: `verbalize_parsed_resume(result) -> str`.

### 4. Answer generation — `agents/resume_analyzer/generate_answers.py`
Mirror the proven isolation harness (`backend/tests/run_resume_analyzer_test.py:49-122`):
- Write each sample's `context.txt` to a temp `.md`.
- `ctx = ResumeAnalysisContext(user_id, resume_id, user_name, resume_text=<context>, local_only=True)`
- `task = _resume_analysis_task(ctx, run_async=False)`; `Crew(agents=[resume_analyzer], tasks=[task]).kickoff(inputs={"resume_path": tmp_md})`
- Read the normalized answer from `ctx.state["json"]`; cache it to the run dir's `answers/<id>.json`.

Support `--answers-from <run_dir>` to reuse cached answers (iterate on metrics without re-running the agent / re-spending tokens).

### 5. Orchestrator — `agents/resume_analyzer/run_eval.py`
```python
from ragas import EvaluationDataset, evaluate
from ragas.dataset_schema import SingleTurnSample
from ragas.metrics import Faithfulness, ResponseRelevancy, AnswerCorrectness
from ragas.run_config import RunConfig

samples = [SingleTurnSample(
    user_input=task_prompt,
    retrieved_contexts=[ctx_text],          # whole resume text, unchunked
    response=verbalize_parsed_resume(answer.result),
    reference=verbalize_parsed_resume(ground_truth.result),
) for each golden sample]

metrics = [Faithfulness(llm=llm), ResponseRelevancy(llm=llm, embeddings=emb),
           AnswerCorrectness(llm=llm, embeddings=emb)]

result = evaluate(EvaluationDataset(samples=samples), metrics=metrics,
                  llm=llm, embeddings=emb,
                  run_config=RunConfig(max_workers=4))   # keep low; agent LLM is max_rpm=10
```
Then write `result.to_pandas()` → `scores.csv`, aggregate means → `summary.json`, plus `run_config.json` (metrics, models, git commit, verbalizer id, dataset version). Results go under `agents/resume_analyzer/<dataset_version>/run_<timestamp>/`.

CLI flags: `--version v1` (dataset version), `--limit N` (smoke subset), `--answers-from <dir>`.

### 6. `.gitignore`
Track `backend/golden_dataset/**` (curated, valuable). For results, track small `summary.json`/`run_config.json` for history but ignore the bulky `answers/` and `scores.csv` — add a rule under `backend/tests/ragas/agents/*/v*/run_*/`.

## Design notes / caveats
- **Reproducibility:** the agent runs on Claude Sonnet 5 with default sampling (Sonnet 5 rejects non-default temperature); the RAGAS judge LLM is Gemini at `temperature=0`. Expect small run-to-run variance on `answer_correctness`.
- **`answer_relevancy` fit:** it judges how well the response answers the `user_input` by generating hypothetical questions from the response. For a pure extraction task whose "question" is a schema-laden instruction, this metric is the least naturally suited of the three — included as requested; read it as a soft signal.
- **Why the context metrics were dropped:** `context_precision`/`context_recall` score a *retrieval* step. The agent has none — the whole resume is always fed in, so there is nothing to rank or miss. Dropping them also removes the only reason to chunk, so the context is passed whole.
- **Cost/rate limits:** three LLM-judged metrics × samples × Gemini calls; keep `RunConfig.max_workers` low to respect the `max_rpm=10` budget and add retries.

## Verification
1. **No key needed:** unit-test the pure helper `verbalize_parsed_resume` (skips empty fields; applied identically to answer & reference) via a quick pytest module.
2. **Dataset bootstrap:** generate `context.txt` for each sample from `sample_data/` via `extract_resume_text`; confirm `ground_truth.json` files validate with `ParsedResume.model_validate_json`.
3. **Live smoke (needs `GEMINI_API_KEY`):** `cd backend && uv run python -m tests.ragas.agents.resume_analyzer.run_eval --version v1 --limit 1` → expect a `run_<ts>/` dir with `scores.csv` (3 metric columns, no NaNs) and `summary.json`.
4. **Full run:** drop `--limit`; sanity-check that a deliberately corrupted ground truth (e.g. wrong employer) lowers `answer_correctness`, confirming the metrics respond to signal.
